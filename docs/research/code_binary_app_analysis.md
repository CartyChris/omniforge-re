# Free/open-source tools for analysing source code, repos, binaries and installed apps (candidates for OmniForge RE)

Research date: 2026-10-18. "Hands-on test" means I installed the package from the npm registry in an isolated directory in this sandbox (Linux x64, Node 22.22.0, Bun 1.4.2) and ran it. I could not run macOS binaries, so every macOS arm64 claim is either from a published artifact name/README or marked unverified. Star counts are from the rendered GitHub page at fetch time. Release dates come from registry metadata (npm, PyPI, Go module proxy, Maven Central, NuGet) or from `releases.atom` feeds.

## Q1. Which candidates can run IN-PROCESS (Vercel serverless function, browser, Bun sidecar) and which are local-CLI only? Concrete packages and versions.

### Takeaway
Three tiers work. (1) Pure WASM/JS libraries run in-process: `web-tree-sitter@0.27.1` plus `@vscode/tree-sitter-wasm@0.3.1` grammars, `@ast-grep/wasm@0.51.0` (Node/browser, but it broke under Bun), `@electron/asar@4.3.1`, `secretlint@13.0.7`, `plist`/`bplist-parser` and `@sqlite.org/sqlite-wasm`. (2) One native addon is Bun-compile safe in my test: `@ast-grep/napi@0.51.0`. (3) All JVM/.NET/Go/Rust/Python/Crystal tools (jadx, apktool, Ghidra, ILSpy, Noir, osv-scanner, syft, semgrep...) are CLI-only on the Mac, or can run on Linux in a Vercel Sandbox microVM.

### Cited Findings
**Tested in-process (hands-on)**
- `web-tree-sitter@0.27.1` (MIT, published 2026-10-08, 4.69 MB unpacked including debug builds and source maps, no dependencies, no install script) is the WASM runtime. The runtime itself is `web-tree-sitter.wasm` 210,415 bytes (83,255 gzipped) plus a 156 KB JS file (32 KB gzipped) — [npm registry](https://registry.npmjs.org/web-tree-sitter), [tarball](https://registry.npmjs.org/web-tree-sitter/-/web-tree-sitter-0.27.1.tgz). Package `exports` has ESM and CJS entry points and a `browser` field that stubs `fs`, `fs/promises` and `module` — same tarball.
- Hands-on: with both `web-tree-sitter@0.26.8` and `0.27.1`, I loaded `@vscode/tree-sitter-wasm` grammars for Python, TypeScript, Go, Java, Rust and C# in Node 22. Queries returned functions, classes, imports, decorators/annotations/attributes and Express-style routes (e.g. `get '/api/users/:id'`). Total time for init, six grammar loads, parses and queries was about 218-224 ms, and RSS was about 98-100 MB. Grammar ABI versions were 14 (TypeScript, Java) and 15 (others) — [@vscode/tree-sitter-wasm tarball](https://registry.npmjs.org/@vscode/tree-sitter-wasm/-/tree-sitter-wasm-0.3.1.tgz).
- Hands-on: `tree-sitter-wasms@0.1.13` (the popular prebuilt bundle, Unlicense, last published 2025-10-07) FAILED to load any grammar under `web-tree-sitter` 0.26.8 and 0.27.1 (error thrown in `getDylinkMetadata`). Its WASM files carry a legacy `dylink` section, while the VS Code grammars use `dylink.0` — [tree-sitter-wasms](https://registry.npmjs.org/tree-sitter-wasms), [tarball](https://registry.npmjs.org/tree-sitter-wasms/-/tree-sitter-wasms-0.1.13.tgz).
- Hands-on: `@repomix/tree-sitter-wasms@0.1.17` (Unlicense packaging, published 2026-04-22, 23.9 MB unpacked, 17 grammars) loaded all 17 files OK under `web-tree-sitter@0.26.8` — [npm](https://registry.npmjs.org/@repomix/tree-sitter-wasms), [tarball](https://registry.npmjs.org/@repomix/tree-sitter-wasms/-/tree-sitter-wasms-0.1.17.tgz). Repomix 1.18.1 itself depends on `web-tree-sitter ^0.27.0` and `@repomix/tree-sitter-wasms ^0.1.17` — [repomix package.json via tarball](https://registry.npmjs.org/repomix/-/repomix-1.18.1.tgz).
- Hands-on: `@ast-grep/wasm@0.51.0` (MIT, 2.28 MB unpacked; `wasm_bg.wasm` 2,220,113 bytes, 807 KB gzipped) declares peer `web-tree-sitter ^0.26.0` (npm refused to install it next to 0.27.1 without `--force`). It found `app.$VERB($ROUTE, $$$H)` matches in TypeScript in about 47 ms in Node 22 (with an ExperimentalWarning about importing WASM modules). It has no built-in languages; each grammar must be registered via `registerDynamicLanguage({ lang: { libraryPath } })` — [@ast-grep/wasm README](https://registry.npmjs.org/@ast-grep/wasm), [tarball](https://registry.npmjs.org/@ast-grep/wasm/-/wasm-0.51.0.tgz).
- Hands-on: `@ast-grep/wasm@0.51.0` FAILED under Bun 1.4.2, both `bun run` and `bun build --compile` (`wasm.__wbindgen_start is not a function`). The README advertises browsers, Deno and edge runtimes, but Bun was not tested by the authors as far as the README shows — same tarball.
- Hands-on: `@ast-grep/napi@0.51.0` (MIT, published 2026-10-15) works in Node 22 (linux-x64), under `bun run`, and inside a `bun build --compile` binary run from an empty directory. Optional platform packages: darwin-x64, darwin-arm64, linux-x64-gnu/musl, linux-arm64-gnu/musl, win32 x64/ia32/arm64. The `darwin-arm64` `.node` file is 7,751,008 bytes. `bun build --compile --target=bun-darwin-arm64` produced a Mach-O arm64 executable (70.0 MB; I could not execute it here). The linux-x64 compiled binary was 97.7 MB vs an 81.3 MB hello-world baseline — [npm @ast-grep/napi](https://registry.npmjs.org/@ast-grep/napi/0.51.0).
- `@ast-grep/napi` ships only the JavaScript-ecosystem languages by default. Other languages need `@ast-grep/lang-*` packages that use a postinstall script to place a per-platform parser library, and `registerDynamicLanguage` may only be called once per process — [ast-grep JS API doc source](https://raw.githubusercontent.com/ast-grep/ast-grep.github.io/main/website/guide/api-usage/js-api.md). The lang packages (e.g. `@ast-grep/lang-python@0.0.6`, ISC, 6.2 MB) have `install_script: true` — [npm](https://registry.npmjs.org/@ast-grep/lang-python). Inference: this is a poor fit for a Bun-compiled sidecar.
- Hands-on: Bun `--compile` can embed `web-tree-sitter.wasm` and grammar `.wasm` files (via `import x from '...wasm' with { type: 'file' }`, loaded as bytes into `Language.load`). The compiled binary (83.5 MB, only +2.2 MB over the 81.3 MB baseline) ran from a directory with no `node_modules` and parsed Python and TypeScript correctly — [web-tree-sitter](https://registry.npmjs.org/web-tree-sitter/-/web-tree-sitter-0.27.1.tgz), [@vscode/tree-sitter-wasm](https://registry.npmjs.org/@vscode/tree-sitter-wasm/-/tree-sitter-wasm-0.3.1.tgz).
- Native addons to avoid in the Bun sidecar: `tree-sitter@0.25.1` (node-gyp-build install script, 4.45 MB) — [npm](https://registry.npmjs.org/tree-sitter); `better-sqlite3@13.0.3` (27 MB unpacked, Node >=22) — [npm](https://registry.npmjs.org/better-sqlite3); `frida@17.24.2` (install script, prebuild-install, LGPL-2.0 WITH WxWindows-exception-3.1, published 2026-10-18) — [npm](https://registry.npmjs.org/frida); `oxc-parser@0.154.0` (19 optional native deps) — [npm](https://registry.npmjs.org/oxc-parser). I did not test these under Bun.

**Third execution tier: Linux microVM via Vercel Sandbox**
- Vercel Sandbox (`@vercel/sandbox`, `Sandbox.create({ image: 'vercel/sandbox/node:26', networkPolicy: 'deny-all', ... })`) runs arbitrary commands via `sandbox.runCommand(cmd, args)` inside a microVM. The REST API exposes `sudo`, `cwd`, `env` and a command `timeout` of up to 5 hours — [Vercel docs search results (SDK reference)](https://vercel.com/docs/sandbox/sdk-reference), [REST execute-command](https://vercel.com/docs/rest-api/sdk/sandboxes/execute-a-command).

### Inferences
- The in-process pair `web-tree-sitter@0.27.1` plus `@vscode/tree-sitter-wasm@0.3.1` (or `@repomix/tree-sitter-wasms@0.1.17`) is the only multi-language parser stack I verified end to end. Pin both versions and keep a load test in CI, because grammar/runtime pairs can break (as `tree-sitter-wasms@0.1.13` did).
- On Vercel, `.wasm` files are read at runtime by path, so the bundler's file tracing must include them (e.g. Next.js `outputFileTracingIncludes`). I did not test this on Vercel.
- Because `@ast-grep/wasm` fails under Bun and `@ast-grep/napi` works, use napi in the sidecar and wasm in the Vercel/browser tier. Do not share one code path.
- For JVM/.NET/Python tools, the Vercel Sandbox is the only way to offer them from the hosted web app. Cost, concurrency and egress limits were not retrieved.
- A Go binary bundled in a Node function bundle may be spawnable on Vercel (Linux x64). I did not verify this or any size limit.

### Gaps
- Vercel Function bundle-size, memory and duration limits and Sandbox pricing/limits: the docs search returned no limits page, and `vercel.com` is not reachable by WebFetch from this sandbox.
- No macOS execution was possible: the darwin-arm64 Bun-compiled binary and darwin napi addon are unverified at runtime.
- Browser (not Node) behaviour of `@electron/asar`, `repomix` and `dependency-cruiser` was not tested.
- Bun behaviour of `secretlint`, `plist`, `repomix` and `dependency-cruiser` was not tested.

## Q2. Best cheap way to get multi-language structure (functions, classes, imports, routes) from arbitrary repos: web-tree-sitter grammar bundle size, ast-grep, ctags?

### Takeaway
Use `web-tree-sitter` with a small, lazily loaded set of grammars. Six common languages cost 4.4 MB raw and 0.48 MB gzipped, and 13 languages cost 20.6 MB raw and 1.8 MB gzipped, from the VS Code grammar package. ast-grep is a pattern layer on tree-sitter, good for route/auth patterns but not a structure extractor. Universal Ctags is GPL-2.0 and spawn-only, so it adds nothing over tree-sitter.

### Cited Findings
- Measured grammar sizes in `@vscode/tree-sitter-wasm@0.3.1` (MIT, 22 MB unpacked, published 2026-04-07), raw / gzip level 6: cpp 5.39 MB / 415 KB; c-sharp 5.10 MB / 312 KB; ruby 2.11 MB / 168 KB; tsx 1.45 MB / 138 KB; typescript 1.41 MB / 136 KB; bash 1.38 MB / 180 KB; rust 1.11 MB / 116 KB; php 1.06 MB / 106 KB; powershell 0.99 MB / 95 KB; python 458 KB / 65 KB; java 415 KB / 51 KB; javascript 412 KB / 50 KB; go 217 KB / 38 KB; css 129 KB / 21 KB; regex 21 KB / 6 KB. Only these 15 grammars are included — [tarball](https://registry.npmjs.org/@vscode/tree-sitter-wasm/-/tree-sitter-wasm-0.3.1.tgz), [npm](https://registry.npmjs.org/@vscode/tree-sitter-wasm).
- Subset totals I computed from that package: JS + TS + TSX + Python + Java + Go = 4.4 MB raw / 0.48 MB gzipped. Adding Rust, C#, C++, PHP, Ruby, Bash and CSS = 20.6 MB raw / 1.80 MB gzipped — same tarball.
- `@repomix/tree-sitter-wasms@0.1.17` file sizes (raw): c_sharp 5.95 MB, cpp 3.47 MB, swift 3.42 MB, ruby 2.13 MB, tsx 1.45 MB, typescript 1.42 MB, rust 1.12 MB, php 1.07 MB, dart 1.0 MB, c 645 KB, solidity 513 KB, python 460 KB, java 417 KB, javascript 416 KB, go 219 KB, css 150 KB, vue 31 KB. It has no Kotlin, Scala, HTML, JSON or YAML grammar — [tarball](https://registry.npmjs.org/@repomix/tree-sitter-wasms/-/tree-sitter-wasms-0.1.17.tgz).
- Gap-fillers: `@lumis-sh/wasm-<lang>` per-language packages (MIT, 0.26.x, e.g. python 481 KB unpacked, published 2026-09-28) exist for Kotlin (`@lumis-sh/wasm-kotlin@0.26.5`), Rust, Bash, Elixir, Markdown and others. Each ships a `.wasm` plus highlight queries in `lumis.json` (not tags/definition queries). `@kreuzberg/tree-sitter-language-pack-wasm@1.10.9` (MIT, 55.8 MB unpacked) bundles 306 languages — [lumis kotlin](https://registry.npmjs.org/@lumis-sh/wasm-kotlin), [lumis python](https://registry.npmjs.org/@lumis-sh/wasm-python), [kreuzberg wasm](https://registry.npmjs.org/@kreuzberg/tree-sitter-language-pack-wasm), [kreuzberg native](https://registry.npmjs.org/@kreuzberg/tree-sitter-language-pack). I did not load-test the lumis or kreuzberg packages.
- Ready-made extraction queries: the `repomix` package ships `lib/core/treeSitter/query*.js` files for C, C#, C++, CSS, Dart, Go, Java, JavaScript, PHP, Python, Ruby, Rust, Solidity, Swift, TypeScript and Vue. Repomix is MIT. Its `--compress` mode uses tree-sitter to keep classes, functions and interfaces — [repomix tarball](https://registry.npmjs.org/repomix/-/repomix-1.18.1.tgz), [Repomix README](https://github.com/yamadashy/repomix).
- Hands-on: my own small queries captured function, class, import, decorator/annotation and Express-style route nodes for Python, TypeScript, Go, Java, Rust and C# with the VS Code grammars (see Q1).
- tree-sitter itself: MIT, 27.2k stars, 3.0k forks, has Rust and Wasm bindings (`lib/binding_web`) — [GitHub](https://github.com/tree-sitter/tree-sitter), [web README](https://raw.githubusercontent.com/tree-sitter/tree-sitter/master/lib/binding_web/README.md). `tree-sitter-cli@0.27.1` was published 2026-10-08 — [npm](https://registry.npmjs.org/tree-sitter-cli).
- ast-grep: MIT, 16.3k stars, "CLI tool for code structural search, lint and rewriting. Written in Rust". Latest releases from the feed: 0.51.0 (2026-10-15), 0.50.0 (2026-10-09), 0.45.3 (2026-08-31) — [GitHub](https://github.com/ast-grep/ast-grep), [releases.atom](https://github.com/ast-grep/ast-grep/releases.atom). `@ast-grep/cli@0.51.0` is a 5.8 KB shim with platform binaries as optional dependencies (7 optional deps, install script) — [npm](https://registry.npmjs.org/@ast-grep/cli).
- Universal Ctags: GPL-2.0, 7.3k stars, rolling tags (latest `p6.2.20261011.0`, 2026-10-08); output formats include `u-ctags`, `e-ctags`, `etags`, `xref` and `json`; Homebrew formula available — [GitHub](https://github.com/universal-ctags/ctags), [releases.atom](https://github.com/universal-ctags/ctags/releases.atom), [output-format doc](https://raw.githubusercontent.com/universal-ctags/ctags/master/docs/output-format.rst). The npm `universal-ctags@0.0.1` (2016, "MIT AND GPL-2.0", emscripten build) is abandoned — [npm](https://registry.npmjs.org/universal-ctags). `mcp-ctags@1.0.1` (MIT, 2026-05-29) wraps ctags plus ripgrep — [npm](https://registry.npmjs.org/mcp-ctags).
- Counters: scc (MIT, 8.8k stars, v3.7.0, complexity, COCOMO, ULOC, JSON/CSV/SQL/HTML output, MCP mode) — [GitHub](https://github.com/boyter/scc); tokei (MIT/Apache-2.0, 15.0k stars, 150+ languages, JSON output, v15.0.0 on 2026-09-06) — [GitHub](https://github.com/XAMPPRocky/tokei), [releases.atom](https://github.com/XAMPPRocky/tokei/releases.atom); cloc (GPL-2.0 Perl, 23.6k stars, v2.10 on 2026-07-04, JSON/YAML/CSV output, also `npm install -g cloc`) — [GitHub](https://github.com/AlDanial/cloc), [releases.atom](https://github.com/AlDanial/cloc/releases.atom).
- Structural indexers: SCIP (Apache-2.0, 831 stars, now `scip-code/scip`; indexers for Java/Scala/Kotlin, TypeScript/JS, Rust, C/C++, Ruby, Python, C#/VB, Dart, PHP) — [GitHub](https://github.com/sourcegraph/scip); Go module `github.com/sourcegraph/scip` tagged v0.10.0 on 2026-09-03 — [Go proxy](https://proxy.golang.org/github.com/sourcegraph/scip/@latest). `@sourcegraph/scip-typescript@0.4.0` (Apache-2.0, npm publish 2025-10-02) needs Node 22 or 24, a `tsconfig.json` (or `--infer-tsconfig`), and dependencies installed — [GitHub](https://github.com/sourcegraph/scip-typescript), [npm](https://registry.npmjs.org/@sourcegraph/scip-typescript). Joern builds code property graphs for C/C++/Java/Binary/JavaScript/Python/Kotlin and has daily releases (v4.0.658 on 2026-10-17) — [GitHub](https://github.com/joernio/joern), [releases.atom](https://github.com/joernio/joern/releases.atom).
- JS/TS architecture: dependency-cruiser (MIT, 7.3k stars, outputs dot/csv/html/mermaid/json; latest 18.6.0 on 2026-10-11) — [GitHub](https://github.com/sverweij/dependency-cruiser); madge (MIT, 10.2k stars, latest 8.0.0 published 2024-08-05, Graphviz needed for image output only) — [GitHub](https://github.com/pahen/madge), [npm](https://registry.npmjs.org/madge); ts-morph (MIT, 6.2k stars, 28.0.0 on 2026-04-12) — [GitHub](https://github.com/dsherret/ts-morph); typedoc 0.28.20 (Apache-2.0, 2026-07-05) — [npm](https://registry.npmjs.org/typedoc).

### Inferences
- Recommended default grammar set: JS, TS, TSX, Python, Java, Go (0.48 MB gzipped), lazily adding Rust, C#, C++, PHP, Ruby, Bash from the same package. Add Kotlin (Android) and Swift/Dart (mobile) from `@lumis-sh` or `@repomix/tree-sitter-wasms`. Fetch each grammar on demand (ranged by file extension) rather than bundling all of them.
- Reusing Repomix's MIT queries saves writing queries for 16 grammars. Routes need framework-specific queries, which should be authored or borrowed from ast-grep-style patterns.
- `madge` has had no release in more than 18 months (2024-08-05), so it is stale by this brief's rule. Prefer dependency-cruiser.
- Tree-sitter plus Noir (Q3) covers structure plus endpoints without any copyleft tools. Ctags and cloc would add GPL spawn-only dependencies for no gain.
- Language counting is already done by OmniForge's detection; scc is only worth adding for complexity/COCOMO numbers.

### Gaps
- I did not fetch the per-grammar `queries/tags.scm` files, so I cannot say how complete upstream tag queries are for each language.
- Parse speed on large files and memory ceilings on Vercel functions were not measured beyond the six-language smoke test.
- typedoc, ts-morph and madge star counts: only ts-morph and madge were fetched. Last-commit dates were not available from the GitHub pages.
- ctags language count and `--output-format=json` build requirements (libjansson) were not verified.

## Q3. Which semgrep/ast-grep rule sets are permissively licensed and useful for routes, API endpoints, auth flows and framework patterns (not just vulnerabilities)?

### Takeaway
No permissively licensed ready-made rule pack for route inventory exists among the semgrep/ast-grep sets I could verify. Semgrep's official rules are under a restrictive Semgrep Rules License and look vulnerability-oriented, and Opengrep's fork of them is archived. The best free route/auth inventory source is OWASP Noir (MIT, 261 framework entries across 32 languages), consumed as CLI output, plus rules OmniForge writes itself in ast-grep or tree-sitter queries.

### Cited Findings
- Semgrep CE engine is LGPL-2.1 (17.1k stars). The `semgrep/semgrep-rules` repo (1.3k stars) says rules are "Free to use under the Semgrep Rules License"; contributions are licensed to Semgrep, Inc. under Semgrep Rules License v. 1.0 — [GitHub semgrep](https://github.com/semgrep/semgrep), [GitHub semgrep-rules](https://github.com/semgrep/semgrep-rules). The repo's LICENSE file only points to semgrep.dev for the terms — [LICENSE](https://raw.githubusercontent.com/semgrep/semgrep-rules/develop/LICENSE).
- Per search-result summaries of Semgrep's own docs: the Rules License covers Semgrep-maintained rules; vendors cannot use them in competing products or SaaS offerings; individuals, consultants and companies using them internally are fine; restrictions apply when "selling a product"; third-party rules in the registry keep their own licenses (Trail of Bits rules are AGPL-3.0); the engine (LGPL-2.1) can be used in your own software without a licence from Semgrep, Inc. I could not open the licence text itself (semgrep.dev is blocked here) — [Semgrep licensing doc](https://docs.semgrep.dev/licensing), [Semgrep OSS update blog](https://semgrep.dev/blog/2024/important-updates-to-semgrep-oss), [WebSearch summary of both](https://docs.semgrep.dev/faq/overview).

## Q4. Android APK / iOS IPA / Electron / .NET: which free tools give readable source or resources, with what licences and macOS arm64 limits?

### Takeaway
Android: jadx (Apache-2.0) plus Apktool (Apache-2.0) are the standard, both JVM-based. iOS: an IPA is a zip with plists (pure-JS parsable), but App Store binaries are FairPlay-encrypted and need a decrypted dump from a jailbroken device before static analysis. Electron: `@electron/asar` extracts app source in-process. .NET: `ilspycmd` (MIT) needs the .NET SDK on the Mac.

### Cited Findings
**Android**
- jadx: Apache-2.0, 51.1k stars. Needs 64-bit Java 11+ (the `with-jre` bundle removes that need). Install by release zip or `brew install jadx`. Inputs: .apk, .dex, .aab, .apks, .apkm, .xapk, .jar, .class, .aar, .smali, .arsc. Output: Java source, decoded resources and AndroidManifest. Flags include `--no-res`, `--no-src`, `--deobf`, `-e/--export-gradle`, `--output-format json`, `--call-graph`, `--cfg`, `-j` threads. The README warns it "can't decompile 100% of the code". Latest on Maven Central is 1.5.6, updated 2026-07-10 — [GitHub](https://github.com/skylot/jadx), [Maven metadata](https://repo1.maven.org/maven2/io/github/skylot/jadx-core/maven-metadata.xml). `jadx-core-1.5.6.jar` is 2.4 MB — [Maven dir](https://repo1.maven.org/maven2/io/github/skylot/jadx-core/1.5.6/).
- Apktool: Apache-2.0, 26.0k stars; decodes resources to near-original form, handles smali, rebuilds; `main` branch is 3.x. 3.0.3 updated on Maven Central 2026-07-20; `apktool-cli-3.0.3.jar` is 22.7 MB. The GitHub page does not state a Java requirement or install steps — [GitHub](https://github.com/iBotPeaches/Apktool), [Maven metadata](https://repo1.maven.org/maven2/org/apktool/apktool-lib/maven-metadata.xml), [Maven dir](https://repo1.maven.org/maven2/org/apktool/apktool-cli/3.0.3/).
- Vineflower (Apache-2.0, 2.4k stars, Fernflower fork) decompiles JVM bytecode; 1.11+ needs Java 17; 1.12.0 updated 2026-04-29; jar 1.6 MB — [GitHub](https://github.com/Vineflower/vineflower), [Maven](https://repo1.maven.org/maven2/org/vineflower/vineflower/maven-metadata.xml).
- Androguard: Apache-2.0, 6.4k stars. APK/DEX/AXML parsing, manifest/permissions, optional decompiler, ARM64 disassembly, vuln scan and an MCP server. PyPI serves 4.1.4 while the repo is on a v5 line that needs a Rust toolchain for extras; docs are flagged "in progress" — [GitHub](https://github.com/androguard/androguard), [PyPI](https://pypi.org/pypi/androguard/json).
- MobSF: GPL-3.0, 22.0k stars; static analysis of APK, IPA and APPX plus dynamic analysis; REST API; Docker or local Python 3.12+ install; PyPI `mobsf` 4.5.3 (2026-09-21, 99 MB) — [GitHub](https://github.com/MobSF/Mobile-Security-Framework-MobSF), [PyPI](https://pypi.org/pypi/mobsf/json).
- Pure-JS AXML/APK helpers are weak: `android-axml-parser@0.1.0` (MIT, published 2026-07-15, brand new), `app-info-parser@1.1.6` (MIT, 2024-01-08, stale), `adbkit-apkreader@3.2.0` (Apache-2.0, 2020, stale) — [android-axml-parser](https://registry.npmjs.org/android-axml-parser), [app-info-parser](https://registry.npmjs.org/app-info-parser), [adbkit-apkreader](https://registry.npmjs.org/adbkit-apkreader).
- `apk-mitm@1.3.0` (MIT, 2024-04-21) and `@zhuma4/apk-decompile@4.4.2` (Apache-2.0, 2026-06-30, jadx + apktool wrapper) exist on npm, but I did not vet them — [search](https://registry.npmjs.org/-/v1/search?text=apktool).

**iOS**
- Static analysis of App Store binaries: they are FairPlay-encrypted. Check `LC_ENCRYPTION_INFO` `cryptid` via `otool -l` (1 = encrypted). Decrypting generally needs a jailbroken device (e.g. frida-ios-dump). Patching `cryptid` alone does not decrypt. These are community write-ups, not Apple docs — [noh.am](https://noh.am/en/posts/decrypting/), [tessl iOS static skill](https://tessl.io/registry/skills/github/PurpleAILAB/Decepticon/reverser-ios-static).
- Frida on iOS: `frida-server` on a jailbroken device injects even into encrypted apps; the non-jailbroken route embeds Frida Gadget in a re-signed IPA and only works if the binary is not FairPlay-encrypted — [NCC Group](https://www.nccgroup.com/research/ios-instrumentation-without-jailbreak/), [OWASP MASTG TECH-0090](https://mas.owasp.org/MASTG/techniques/ios/MASTG-TECH-0090).
- ipsw (MIT, 3.8k stars; Go; `brew install blacktop/tap/ipsw`): IPSW download, dyld shared cache extract, `ipsw class-dump`, `ipsw macho disass`, `ipsw macho info` (load commands, symbols, signatures, entitlements). The page does not mention IPA files; building from source needs Go 1.26+ and CGO. The Go module has no semver tag but a commit pseudo-version dated 2026-10-15 — [GitHub](https://github.com/blacktop/ipsw), [Go proxy](https://proxy.golang.org/github.com/blacktop/ipsw/@latest).
- LIEF (Apache-2.0, 5.6k stars; ELF, PE, Mach-O, COFF, OAT, DEX, VDEX, ART; C++, Python, Rust). No official JS/WASM binding (a third-party "unofficial, AI-generated" Node binding is linked) — [GitHub](https://github.com/lief-project/LIEF), [PyPI](https://pypi.org/pypi/lief/json).
- Info.plist and entitlements text: `plist@5.0.0` and `bplist-parser@0.5.0` (both MIT) handle XML and binary plists — [plist](https://registry.npmjs.org/plist), [bplist-parser](https://registry.npmjs.org/bplist-parser).
- `hermes-dec` (React Native Hermes bytecode decompiler; PyPI 0.1.8 published 2026-10-15) is AGPL-3.0-or-later; `reflutter` 0.9.8 (2026-09-24) is GPLv3+ — [hermes-dec GitHub](https://github.com/P1sec/hermes-dec), [PyPI hermes-dec](https://pypi.org/pypi/hermes-dec/json), [PyPI reflutter](https://pypi.org/pypi/reflutter/json).

**Electron**
- `@electron/asar` 4.3.1 (MIT): `list`, `extract-file`, `extract`; files in `unpack`/`unpackDir` stay outside the archive; per-file SHA256 integrity blocks — [GitHub](https://github.com/electron/asar), [npm](https://registry.npmjs.org/@electron/asar).
- Electronegativity (Apache-2.0, 1.1k stars): scans Electron configs, accepts `.asar`, SARIF/CSV output. The README states "We're no longer actively maintaining this project"; the last release is v1.10.0 (2022-12-07) — [GitHub](https://github.com/doyensec/electronegativity), [releases.atom](https://github.com/doyensec/electronegativity/releases.atom).

**.NET**
- ILSpy (MIT, 26.7k stars). `ilspycmd` is a `dotnet tool` (NuGet package type DotnetTool); latest `11.1.0.9782` published 2026-09-23. The ILSpy README says ILSpy.csproj targets .NET 10.0 and that running on Unix/Mac needs the .NET 10.0 SDK. It does not call out macOS arm64 explicitly. **Native / general**
- Ghidra: Apache-2.0, 90.8k stars, "JDK 25 64-bit is required" per the README; latest releases 12.1.4 (2026-09-21), 12.1.3 (2026-08-18), 12.1.2 (2026-06-05); runs on Windows, macOS, Linux; scripting in Java and Python (PyGhidra needs Python 3.9-3.15 to build). The page does not mention `analyzeHeadless`, macOS arm64 natives or install size — [GitHub](https://github.com/NationalSecurityAgency/ghidra), [releases.atom](https://github.com/NationalSecurityAgency/ghidra/releases.atom). PyPI `pyghidra` 3.1.0 (Apache-2.0, 2026-05-14) — [PyPI](https://pypi.org/pypi/pyghidra/json).

Rizin: page lists LGPL-3.0 and GPL-3.0, 4.0k stars, v0.9.1 on 2026-06-29 — [GitHub](https://github.com/rizinorg/rizin), [releases.atom](https://github.com/rizinorg/rizin/releases.atom).

### Inferences
- The Mac setup wizard should detect Java version (11+ for jadx; 17+ for Vineflower; 21 for Joern; 25 for Ghidra) and .NET 10 SDK; the jadx `with-jre` bundle avoids the Java requirement for jadx only.

- Frida needs devices, jailbreak or re-signing and carries safety/legal risk. Keep it opt-in and out of the first phase.

### Inferences
- Rule for the integration layer: copyleft and restricted tools may only be detected and driven as separate processes on the user's Mac after approval, never vendored, linked or shipped in the Tauri bundle or the Vercel deployment. Copyleft output (JSON reports) is data, not a derivative of the tool, but the legal position should be confirmed.
- AGPL tools should not be run by OmniForge on a hosted server (e.g. Vercel Sandbox) on behalf of other users, to avoid network-use obligations. TruffleHog's live-verification calls would also leak candidate secrets to third-party services, so if ever invoked it must pass `--no-verification`.
- Prefer gitleaks/Betterleaks rule data (MIT) or secretlint (MIT) over TruffleHog for secret scanning.
- LGPL tools (Semgrep CE, Opengrep, radare2, rizin) are fine to spawn. Do not static-link their libraries.
- Pin and checksum-verify every downloaded CLI (the Trivy incident is the cautionary example).

### Gaps
- I did not read full licence texts for rizin, radare2 plugins, quark-engine (PyPI licence field empty), `@kreuzberg` packs, or the grammar repos behind the WASM bundles. The Unlicense on the packaging does not necessarily cover each upstream grammar licence (most upstream grammars are MIT, unverified here).
- I did not research whether Semgrep CE's `semgrep-core` bundles any third-party copyleft components.
- No legal review; the AGPL hosted-service and Semgrep Rules License readings are inferences.

## Q7. Ranked catalogue: which tools should OmniForge integrate, with per-tool facts (what it does, licence, maintenance, integration mode, size, duplication)?

### Takeaway
Ranking by value, effort and risk: (1) tree-sitter WASM stack, (2) Noir, (3) ast-grep napi/wasm, (4) jadx + Apktool, (5) in-process secret scanning (secretlint + gitleaks rule data), (6) `@electron/asar` + plist parsers, (7) syft + grype / osv-scanner, (8) Repomix, then heavier items (Ghidra headless, ilspycmd, dependency-cruiser/SCIP, Joern, ScanCode/licensee, scc/tokei, radare2/ipsw, Frida). Avoid: CodeQL, TruffleHog, Semgrep official rules, MobSF/hermes-dec bundling, madge, Electronegativity, `tree-sitter-wasms@0.1.13`.

### Inferences
- A sensible build order: (a) tree-sitter stack plus Repomix queries into the analyzer package; (b) Noir and jadx/apktool as bridge-driven tools with output parsers (Noir OpenAPI to existing OpenAPI ingestion; jadx output directory to existing source analysis); (c) secretlint and gitleaks rule data into the secret layer; (d) asar/plist extraction; (e) syft/grype/osv-scanner behind the bridge; later Ghidra headless and the rest.
- Each CLI integration should have a failable fixture test (e.g. a tiny sample APK for jadx, a sample Express app for Noir) so "detected" and "works" stay separate.
- The Vercel Sandbox gives the hosted app a path to run the same CLIs without the Mac, but only for permissively licensed tools.
