# MCP servers, clients, SDKs and registries for OmniForge RE

_Research date: 2026-10-18. Method: spec/SDK/registry docs read from their GitHub source (raw.githubusercontent.com), packages checked via the npm registry and PyPI JSON APIs, candidate repos verified by shallow `git clone` / `git ls-remote` (last-commit date, LICENSE text, README, tool lists) and the live official registry API. Sandbox egress blocked modelcontextprotocol.io, vercel.com, supabase.com, figma.com, smithery.ai, glama.ai, pulsemcp.com, mcp.so, docs.tavily.com, firecrawl.dev, context7.com, brave.com, exa.ai and docs.github.com (HTTP 403 from the proxy; WebFetch could not resolve most hosts). Claims taken from web-search excerpts (not fetched pages) are labelled "search excerpt"._

## 1. What is the current MCP spec revision and SDK version (Oct 2026), and what changed recently?

### Takeaway
The current spec revision is **2026-07-28** (latest in the docs nav; `2025-11-25` and `2025-06-18` are earlier). The TypeScript SDK **v2** (split packages `@modelcontextprotocol/client` / `server`, 2.3.1 on 2026-10-05, Apache-2.0) is now the stable line and implements it; v1 (`@modelcontextprotocol/sdk` 1.32.1) is in maintenance. The 2026-07-28 revision is a large break: stateless protocol (no `initialize`, no sessions), multi-round-trip requests replacing server-initiated requests, tasks moved to an extension, and Roots/Sampling/Logging/DCR/HTTP+SSE deprecated.

### Cited Findings
**Spec revision and lifecycle**
- Docs navigation lists "Version 2026-07-28 (latest)" followed by 2025-11-25 and 2025-06-18, plus a separate `draft` track — [docs.json](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/docs.json)
- 2026-07-28 changelog, major changes: (1) removes protocol-level sessions and `Mcp-Session-Id` from Streamable HTTP; list endpoints no longer vary per connection; (2) removes the `initialize`/`initialized` handshake — every request carries protocol version + client capabilities in `_meta`; (3) adds mandatory `server/discover`; (4) replaces the HTTP GET endpoint and `resources/subscribe` with `subscriptions/listen`; (5) removes `ping`, `logging/setLevel`, `notifications/roots/list_changed`; (6) moves experimental tasks into official extension `io.modelcontextprotocol/tasks` (polling via `tasks/get`, new `tasks/update`, `tasks/list` removed); (7) introduces Multi Round-Trip Requests (MRTR): servers return `InputRequiredResult` (`resultType: "input_required"`) carrying `roots/list`, `sampling/createMessage`, `elicitation/create` requests and clients retry with `inputResponses`; (8) every result has `resultType`; (9) removes SSE stream resumability (`Last-Event-ID`) — [changelog](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/changelog.mdx)
- Minor changes in the same revision: `extensions` field in capabilities; OpenTelemetry trace-context `_meta` keys; deterministic `tools/list` order; required `Mcp-Method`/`Mcp-Name` request headers on Streamable HTTP POSTs; `ttlMs` + `cacheScope` on list/read results; resource-not-found error code changed to -32602; clients MUST validate RFC 9207 `iss`; DCR clients must send `application_type`; client credentials keyed by issuer; `inputSchema`/`outputSchema` loosened to any JSON Schema 2020-12 and `structuredContent` to any JSON value; `notifications/elicitation/complete` removed — [changelog](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/changelog.mdx)
- Deprecated in 2026-07-28: Roots, Sampling, Logging (SEP-2577); HTTP+SSE transport and `includeContext` "thisServer"/"allServers" (SEP-2596); OAuth Dynamic Client Registration (in favour of Client ID Metadata Documents). Deprecated features need a minimum twelve-month window; none removed yet — [changelog](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/changelog.mdx); [deprecated registry](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/deprecated.mdx)
- Suggested migrations for deprecated features: pass directories/files via tool params, resource URIs or server config instead of Roots; call LLM provider APIs directly instead of Sampling; log to stderr/OpenTelemetry instead of Logging — [changelog](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/changelog.mdx)
- Tasks extension: durable task handle (`CreateTaskResult`, `resultType: "task"`), statuses `working`/`input_required`/`completed`/`failed`/`cancelled`, client capability `io.modelcontextprotocol/tasks`, server decides per request whether to create a task; mid-flight input via `tasks/update`; cancellation `tasks/cancel`. Spec lives in the `modelcontextprotocol/ext-tasks` repo (exists, HEAD verified via git) — [tasks overview](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/extensions/tasks/overview.mdx)
- Tool annotations (`ToolAnnotations`): `title`, `readOnlyHint` (default false), `destructiveHint` (default true; meaningful only when not read-only), `idempotentHint` (default false), `openWorldHint` (default true). Spec: clients MUST treat annotations as untrusted unless from trusted servers; there SHOULD be a human in the loop able to deny tool calls — [schema.ts](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/schema/2026-07-28/schema.ts); [server/tools](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/server/tools.mdx)
- Structured output: `outputSchema` optional per tool; `structuredContent` returned in results — [server/tools](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/server/tools.mdx)
- Elicitation has two modes: form (structured fields; servers MUST NOT request passwords/API keys/tokens/payment credentials) and URL (out-of-band, for sensitive data/OAuth; client must show target domain and get consent). Under 2026-07-28 elicitation is delivered inside MRTR `InputRequiredResult` — [client/elicitation](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/client/elicitation.mdx)
- Authorization (2026-07-28): clients SHOULD support Client ID Metadata Documents (CIMD) (HTTPS URL as `client_id`, document must contain `client_id`, `client_name`, `redirect_uris`); priority order is pre-registered > CIMD > DCR > manual; MUST implement RFC 8707 resource indicators; MUST validate `iss` (RFC 9207); MUST NOT send tokens other than those issued by the MCP server's own authorization server; access tokens MUST NOT go in the query string — [authorization](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/index.mdx); [client-registration](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/client-registration.mdx)
- SDK tiering (published 2026-02-23): Tier 1 requires 100% conformance tests, issue triage within 2 business days, critical bug resolution within 7 days; tasks/extensions are not required for any tier — [sdk-tiers](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/community/sdk-tiers.mdx)

### Inferences
- Build against **v2** (`@modelcontextprotocol/client` ^2.3) from the start. Its default is still the legacy handshake, so the real-world server population (most published servers are still 2025-era) works unchanged, while `mode: 'auto'` future-proofs for 2026-07-28 servers. v1 is only needed if a dependency pins it.
- Do **not** implement Roots, Sampling or Logging — all three are deprecated with a ≥12-month window; pass project directories explicitly (args/tool params). Elicitation (form + URL) is the one server→client feature worth building.
- Tasks are an optional extension, so tools must work without it; do not make it a dependency.
- Because the protocol is now stateless and request-scoped, a serverless (Vercel function) MCP proxy or server is feasible in a way it was not under session-based 2025-03-26…2025-11-25 Streamable HTTP.

### Gaps
- modelcontextprotocol.io (rendered spec site) was unreachable from the sandbox; all spec facts were read from the GitHub `.mdx`/`.ts` sources, which are the same content.
- Did not verify how many public servers already speak 2026-07-28 vs 2025-era; the SDK docs only say deployed 2025 servers are common.
- Whether Claude Code / Codex / Gemini CLI / OpenCode / Aider (the CLIs OmniForge's bridge spawns) already accept per-invocation MCP config flags was not verified (only `claude mcp add …` usage appears in candidate READMEs, e.g. [GitHub MCP README](https://raw.githubusercontent.com/github/github-mcp-server/main/README.md)).

## 2. How to add an MCP client to OmniForge: transports, auth, what works in browser vs Vercel function vs desktop sidecar, and the minimal safe design

### Takeaway
The v2 client's **root entry is runtime-neutral** (no Node builtins), so Streamable HTTP + OAuth can be bundled into the browser build, but a browser can only reach remote servers that allow the web origin via CORS and that tolerate the new custom request headers/Origin checks; **stdio spawning is Node-only (`/stdio` subpath) and must live in the desktop sidecar**. The minimal safe design is a desktop-first client in the sidecar (stdio + Streamable HTTP + OAuth with Keychain tokens) with tool-definition pinning, annotation-driven approvals and sandboxed stdio, plus a restricted, allow-listed remote-only path for the web build via an SSRF-guarded Vercel function.

### Cited Findings
**Transports and runtimes**
- "The root entry of every package is **runtime-neutral**: its module graph never reaches `node:child_process`… Importing `./stdio` is the explicit opt-in to a process runtime." `import { Client } from '@modelcontextprotocol/client'` "runs anywhere: browsers, Workers, Node"; `StdioClientTransport` is Node-only under `@modelcontextprotocol/client/stdio` — [packages doc](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/get-started/packages.md)
- Verified in the tarball: `dist/index.mjs` contains no `child_process`/`cross-spawn` reference while `dist/stdio.mjs` does; `package.json` exports map has `browser`, `workerd` and `node` shims; the browser shim only sets `CORS_IS_POSSIBLE = true` (flags that a `fetch` `TypeError` may be a CORS failure) — [client@2.3.1 tarball](https://registry.npmjs.org/@modelcontextprotocol/client/-/client-2.3.1.tgz)
- Transports: `StreamableHTTPClientTransport(new URL(...), { authProvider, fetch })` for remote; `StdioClientTransport({ command, args, env, cwd, stderr, maxBufferSize })` for local (close sequence: close stdin → SIGTERM → SIGKILL); `SSEClientTransport` as fallback for SSE-only servers (try Streamable HTTP first, retry on a fresh `Client`); `InMemoryTransport.createLinkedPair()` for tests — [connect](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/clients/connect.md); [stdio.d.mts in tarball](https://registry.npmjs.org/@modelcontextprotocol/client/-/client-2.3.1.tgz)
- `StdioClientTransport` default environment: only `HOME, LOGNAME, PATH, SHELL, TERM, USER` on POSIX (a fixed Windows list) via `getDefaultEnvironment()`; default `stderr: "inherit"`; default max buffer 10 MB — [stdio.mjs / stdio.d.mts in tarball](https://registry.npmjs.org/@modelcontextprotocol/client/-/client-2.3.1.tgz)
- Client `fetch` can be wrapped with `createMiddleware`/`applyMiddlewares` (add headers, retry, tracing — and, by extension, URL policy) and passed as the transport's `fetch` option — [middleware doc](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/clients/middleware.md)
- Spec Streamable HTTP (2026-07-28): every JSON-RPC message is a new POST with `Accept: application/json, text/event-stream`; request metadata headers (`Mcp-Method`, `Mcp-Name`) required on each POST; server replies JSON or an SSE stream; no server→client requests on the stream (MRTR instead); no GET/DELETE/session id; stream loss = re-issue the request; servers MUST validate `Origin` (403 if invalid) to stop DNS rebinding; local servers SHOULD bind 127.0.0.1 — [streamable-http](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx)
- The spec pages I downloaded (streamable-http, authorization, tools, elicitation, security) contain no mention of "CORS"/"Access-Control". The SDK docs state: "One browser exception: an opaque CORS `TypeError` during the probe falls back to the legacy era, because deployed 2025 servers commonly have allow-lists that predate the 2026 headers" — i.e. browser clients hit CORS failures against servers whose allow-lists predate the new `Mcp-*` request headers — [protocol-versions](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/protocol-versions.md)
- Server-side helper in the SDK: `hostHeaderValidationResponse(request, [hosts])` / `originValidationResponse(request, [origins])`; "A request without an `Origin` header always passes"; the handler itself does no Host/Origin validation — [web-standard serving](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/serving/web-standard.md)
- Backward compat for HTTP+SSE servers: POST first; on 400/404/405 with a non-modern body, GET and expect an `endpoint` SSE event — [streamable-http](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx)
- Vercel's hosted MCP (`https://mcp.vercel.com`, OAuth, Beta) "only supports AI clients that have been reviewed and approved by Vercel" — search excerpt of [Vercel docs](https://vercel.com/docs/ai-tooling/vercel-mcp)

**Auth / OAuth in the client**
- Pass an `OAuthClientProvider` as `authProvider`; the provider supplies storage for tokens, client info, PKCE verifier, discovery state, `redirectToAuthorization(url)`, `state()`; client info must be keyed by `ctx.issuer`; `connect()` throws `UnauthorizedError` after redirect; finish with `transport.finishAuth(params)` (validates `iss`, throws `IssuerMismatchError`), then reconnect on a fresh transport; SDK does **not** validate `state` itself; docs say tokens belong in OS keychain/secure storage, "never plain files" — [oauth doc](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/clients/oauth.md)
- CIMD example: the client hosts a JSON document at an HTTPS URL containing `client_id` (= that URL), `client_name`, `redirect_uris` (the example lists `http://127.0.0.1:3000/callback` and `http://localhost:3000/callback`), `grant_types: ["authorization_code"]`, `token_endpoint_auth_method: "none"` — [client-registration](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/client-registration.mdx)
- `ClientCredentialsProvider`, `PrivateKeyJwtProvider`, `CrossAppAccessProvider` exist for non-interactive auth (docs page `clients/machine-auth`) — [machine-auth doc exists](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/clients/machine-auth.md); exports in [tarball](https://registry.npmjs.org/@modelcontextprotocol/client/-/client-2.3.1.tgz)

**Server→client features in the v2 client**
- Declare capabilities in the `Client` constructor (`sampling: {}`, `elicitation: { form: {}, url: {} }`; empty `elicitation: {}` means form only); one `client.setRequestHandler('elicitation/create', …)` handler serves both the legacy push path and the modern MRTR path; `inputRequired` option caps automatic round-trips; sampling handler is marked Deprecated (SEP-2577) — [server-requests](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/clients/server-requests.md)

**Host-side patterns recommended by the MCP project**
- Progressive tool discovery: don't inject every tool definition up front; switch to a `search_tools`/`get_tool_details` meta-tool once definitions exceed roughly 1–5% of context; cache definitions, refresh on `list_changed`; avoid re-sorting the tools array mid-conversation (prompt-cache invalidation); follow `ttlMs`/`cacheScope` — [client best practices](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/docs/2026-07-28/develop/clients/client-best-practices.mdx)
- Programmatic tool calling ("code mode") needs a no-network sandbox, host-held credentials, per-call authorization (approving a script ≠ blanket approval), and treats tool results from one server as untrusted input to another — [client best practices](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/docs/2026-07-28/develop/clients/client-best-practices.mdx)
- `@anthropic-ai/sandbox-runtime` (`srt`): Apache-2.0, 0.0.80 (2026-10-16), "lightweight sandboxing tool for enforcing filesystem and network restrictions on arbitrary processes at the OS level, without requiring a container", uses `sandbox-exec` on macOS and `bubblewrap` on Linux plus proxy-based network filtering, explicitly usable for "local MCP servers"; labelled Beta Research Preview — [README](https://raw.githubusercontent.com/anthropics/sandbox-runtime/main/README.md); [npm](https://registry.npmjs.org/@anthropic-ai/sandbox-runtime)
- Docker MCP Gateway runs catalog servers "each in an isolated Docker container", with npx/uvx servers "granted minimal host privileges"; requires Docker Desktop 4.59+ for the MCP Toolkit; supports `--transport streaming` — [docker/mcp-gateway README](https://raw.githubusercontent.com/docker/mcp-gateway/main/README.md)

### Inferences
**Where each piece can run**
| Capability | Browser (static SPA) | Vercel function | Desktop sidecar (Bun-compiled Node) |
|---|---|---|---|
| `Client` + `StreamableHTTPClientTransport` | Yes (root entry), but only for servers whose CORS/Origin policy admits the SPA origin and allows `Mcp-*` + `MCP-Protocol-Version` headers | Yes (plain `fetch`, per-request) | Yes |
| stdio servers (`/stdio`) | No (cannot spawn) | Not a sensible target (typical serverless constraints on child processes/filesystem; not verified against Vercel docs) | **Yes — only place** |
| OAuth redirect flow | Possible (SPA redirect), but tokens would sit in browser storage → XSS-exposed | Not suited (needs durable token store + user redirect) | Best: loopback callback, tokens in macOS Keychain (OmniForge already has Keychain access) |
| Legacy SSE fallback | Possible | Possible but long-lived streams are awkward on serverless | Yes |
| `subscriptions/listen` long-lived stream | Possible | Poor fit (duration limits) — use `ttlMs` polling | Yes |

**Minimal safe design (recommended)**
1. **Sidecar owns all MCP I/O.** Browser UI → existing loopback bridge → sidecar `McpManager` (one `Client` per configured server). Keeps secrets, child processes and OAuth tokens out of the web context and reuses the bridge's existing trust boundary.
2. **Config model:** `{id, label, transport: stdio|http, command/args/cwd | url, envRefs/headerRefs (Keychain keys, never inline secrets), pinnedVersion, toolPins{name→sha256}, allowedTools, approvalMode, source: registryId@version|manual}`. Presets for vetted servers ship in-app with **pinned versions** (many READMEs say `@latest` — do not copy that).
3. **Tool exposure to the agent harness:** namespace as `mcp.<server>.<tool>`; reuse the harness's existing "run command with approval" UI. Approval policy derived from annotations *but never trusted for auto-approval unless the server is user-trusted*: `readOnlyHint:true` + `openWorldHint:false` → may be auto-approved by user setting; everything else (destructive default is `true`, open-world default is `true`) → ask each call, showing exact arguments. Log every call to the existing audit trail.
4. **Rug-pull / poisoning controls:** hash canonical `{name, description, inputSchema, outputSchema, annotations}` at first approval; on any `list_changed`, TTL refresh or reconnect, diff and re-prompt on change; show descriptions to the user before enabling; cap description length; keep the enabled roster small (the MCP project's own advice).
5. **Result handling:** treat tool output as untrusted data (delimit, size-cap, never executed as instructions); block automatic follow-up writes after a result from an open-world tool without a fresh approval (cross-server data flow rule).
6. **Stdio hardening:** show the exact, untruncated command + env keys before first run; spawn with `getDefaultEnvironment()` plus only that server's declared secrets; set `stderr:'pipe'` to capture logs; run under `srt` (macOS Seatbelt) or a container with project dir only (read-only when possible) and egress allow-list/none for local-only servers; require pinned package versions; remember a Bun-compiled sidecar will still need host `node`/`npx`/`uvx` to start npm/PyPI servers.
7. **OAuth:** host the CIMD JSON on the existing Vercel site (static file, HTTPS URL with a path) and use loopback redirect URIs in the desktop app; PKCE + `resource` + `iss` validation come from the SDK, but **OmniForge must compare `state`** itself; key stored credentials by issuer; open the authorization URL only if scheme is `http(s)` and via the Tauri opener (not a shell); run all discovery fetches (`/.well-known/oauth-protected-resource`, AS metadata) through the existing SSRF guard.
8. **Protocol negotiation:** `versionNegotiation:{mode:'auto'}` for HTTP; keep the default (legacy) for stdio because the SDK's stdio probe spawns an extra sibling process; persist `getDiscoverResult()` as a cached `prior`.
9. **Elicitation:** implement form + URL modes in the UI; refuse form fields that look like secrets; no Sampling/Roots handlers.
10. **Context cost:** adopt progressive discovery (`search_tools`) once MCP tool definitions exceed ~2–5% of the active model's context — important for Ollama/small local models.
11. **Web build (Phase 2):** remote-only, allow-listed hosts, proxied by a Vercel function that reuses the crawler's SSRF guard (HTTPS only, private/link-local/metadata ranges blocked, redirect re-validation, DNS pinning), no server-side credential storage, per-origin rate limits. Direct browser connection only when a CORS probe on "Add server" succeeds.
12. **Anthropic provider shortcut (optional, later):** the Messages API MCP connector could call user-approved remote servers server-side, but it bypasses OmniForge's pinning/approval and covers tool calls only — keep the provider-agnostic OmniForge client as the default, since Ollama/OpenAI-compatible/Gemini providers need it anyway.

### Gaps
- Vercel function limits (max duration, streaming/SSE behaviour, outbound restrictions) could not be verified — vercel.com was blocked; Phase 2 feasibility rests on the stateless spec design only.
- Whether popular remote servers (Context7, Exa, Tavily, Supabase, GitHub, Figma) send permissive CORS headers for arbitrary web origins was not tested (hosts blocked); only the official registry API was confirmed to send `access-control-allow-origin: *`.
- Whether `StdioClientTransport`/`cross-spawn` works inside a `bun build --compile` binary was not tested here; the SDK README only claims Node/Bun/Deno support.
- Loopback redirect-URI port flexibility with CIMD (fixed ports in the example) is authorization-server dependent and unverified.
- Tauri-specific details (opener plugin, Keychain API surface) were out of scope.

## 3. Public MCP registries: do they offer free machine-readable APIs for in-app discovery, and under what licence/terms?

### Takeaway
Only the **official registry (registry.modelcontextprotocol.io)** is verified usable: unauthenticated JSON API, `access-control-allow-origin: *`, cursor pagination, ≥4,000 latest-version entries, metadata dedicated to CC0 — but it is a preview-era metaregistry with namespace-ownership checks only (lookalike/spam entries exist, and entries lag package registries). Smithery, Glama and PulseMCP require API keys (Glama also mandates visible attribution); GitHub's MCP Registry and mcp.so have no verified public API.

### Cited Findings

## 4. Documented security risks (tool poisoning, rug pulls, confused deputy, etc.) and mitigations OmniForge should enforce

### Takeaway
The MCP project itself states there is **no protocol-level boundary** for stdio servers (client and server share one trust domain) and that tool definitions are untrusted model instructions that can change after approval; its prescribed mitigations are container/sandbox isolation, per-server scoped credentials, filesystem/egress limits, tool-definition pinning with re-prompting, exact-command consent, SSRF-safe OAuth discovery and URL validation. Real incidents (mcp-remote RCE, Inspector RCE, mcp-server-git CVEs, the first malicious npm MCP server) show these are not theoretical.

### Cited Findings
**Spec/project guidance**
- stdio trust model: "the client and a stdio server share one trust domain… neither the protocol nor the SDKs defend one against the other"; isolation "is the responsibility of the host application"; "treat a third-party local server as untrusted code with exactly the privileges you hand it" — [local-server-security](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/docs/2026-07-28/tutorials/security/local-server-security.mdx)
- Threat list in that guide: malicious server (typosquat/abandoned-takeover), overcollecting server (env vars/files, steered by prompt injection), compromised dependency, **poisoned tool catalog** (tool names/descriptions are instructions; "tool shadowing" targets other servers' tools; a server "can quietly change them after you approved it (a rug pull), so a one-time consent dialog and package pinning do not cover this surface"), vulnerable bridges/local dev servers reachable from web pages — same source
- Mitigations in the guide: read tool descriptions before use (Inspector lists tools without a model); "prefer clients that pin tool definitions" and re-prompt on change; keep server roster small (all servers share model context); run third-party servers in a container with minimal mounts (single highest-leverage mitigation); per-server env/credentials, narrowly scoped tokens, OS secret store; narrowest filesystem root, read-only where possible, allow-lists are only "cooperative boundaries"; `--network=none` for local-only servers, egress allow-list proxy otherwise; 127.0.0.1 binding "is not an authentication boundary" — same source
- Checklist items: version pinned; each server from an identifiable publisher; skim tool descriptions; client re-prompts when a tool definition changes; for fleets, allow-list of approved servers, audit logs, ability to block egress and rotate credentials — same source
- One-click local server config MUST show the exact command untruncated, flag it as dangerous, require explicit approval; SHOULD highlight dangerous patterns (`sudo`, `rm -rf`, network ops, sensitive paths) and run servers sandboxed with minimal default privileges — [security best practices: Local MCP Server Compromise](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx)
- OAuth authorization URLs from a malicious server can be `javascript:` URLs (XSS) or shell-injection payloads; combined with a proxy that spawns stdio processes this escalates to RCE — same source (OAuth Authorization URL Validation; stdio Transport Security in Proxy Scenarios)
- Client SSRF during OAuth discovery: enforce HTTPS (loopback exempt), block private/link-local/metadata ranges (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, fc00::/7, fe80::/10), "avoid implementing IP validation manually" (octal/hex/IPv4-mapped tricks), validate every redirect hop, use an egress proxy (e.g. Smokescreen) for server-side clients, beware DNS TOCTOU (pin resolution) — same source
- Confused deputy (MCP proxy servers with static client IDs + DCR + consent cookies): per-client consent, exact `redirect_uri` match, single-use short-lived `state`; **token passthrough is forbidden** (servers must not accept/forward tokens not issued to them); mix-up attacks (validate `iss`); scope minimization (start with low-risk scopes, step-up via `WWW-Authenticate scope`); state-handle hijacking (servers must not treat possession of a handle as authentication; bind handles to the authenticated user) — same source
- Tools spec: "there SHOULD always be a human in the loop with the ability to deny tool invocations"; annotations untrusted unless from trusted servers — [server/tools](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/server/tools.mdx)
- Client best practices (code mode): "Tool results from one server are untrusted input to another… output truncation alone does not prevent exfiltration"; approving a script ≠ approving each call — [client best practices](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/docs/2026-07-28/develop/clients/client-best-practices.mdx)
- Reference servers are explicitly "not… production-ready solutions… educational examples" — [servers README](https://raw.githubusercontent.com/modelcontextprotocol/servers/main/README.md)
- Playwright MCP: "Playwright MCP is **not** a security boundary"; its `--allowed-origins` "does not serve as a security boundary" — [Playwright MCP README](https://raw.githubusercontent.com/microsoft/playwright-mcp/main/README.md)
- Chrome DevTools MCP "exposes content of the browser instance to the MCP clients allowing them to inspect, debug, and modify any data in the browser"; usage statistics are on by default (`--no-usage-statistics` to opt out) and performance tools may send trace URLs to the Google CrUX API (`--no-performance-crux`) — [chrome-devtools-mcp README](https://raw.githubusercontent.com/ChromeDevTools/chrome-devtools-mcp/main/README.md)

**Incidents / tooling (secondary sources, search excerpts)**
- Invariant Labs coined "tool poisoning" and shipped MCP-Scan with hash-based **tool pinning** against rug pulls; Snyk acquired Invariant (June 2025) and rebranded it Snyk Agent Scan — [Invariant launch post](https://invariantlabs.ai/blog/introducing-mcp-scan). Verified in git: `invariantlabs-ai/mcp-scan` and `snyk/agent-scan` resolve to the same HEAD commit; `snyk/agent-scan` is Apache-2.0, last commit 2026-10-15; its README says analysis sends component information (agent app details, MCP server configurations/signatures) to the Agent Scan API and requires `SNYK_TOKEN`; scanning an MCP config can execute stdio commands or contact remote URLs — [agent-scan README](https://raw.githubusercontent.com/snyk/agent-scan/main/README.md)
- mcp-remote CVE-2025-6514 (CVSS 9.6): OS command injection via a malicious server's `authorization_endpoint`; affected 0.0.5–0.1.15, fixed 0.1.16 (current npm 0.15.1) — search excerpts of [Wiz](https://www.wiz.io/vulnerability-database/cve/cve-2025-6514), [NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-6514); [npm mcp-remote](https://registry.npmjs.org/mcp-remote)
- MCP Inspector CVE-2025-49596: unauthenticated client↔proxy channel allowed RCE via stdio launch; fixed in 0.14.1 (one source says "0.14.1 and earlier" — conflict; GHSA wording is "below 0.14.1") — search excerpts of [OSV](https://osv.dev/vulnerability/CVE-2025-49596), [AhnLab](https://asec.ahnlab.com/en/88812/)
- Official `mcp-server-git`: CVE-2025-68143 (`git_init` arbitrary path; tool removed), CVE-2025-68144 (flag-injection in `git_diff`/`git_checkout`), CVE-2025-68145 (`--repository` scope escape), fixed late 2025 (sources disagree 2025.12.17 vs 12.18); a further `git_add` path issue CVE-2026-27735 fixed in 2026.1.14 — search excerpt of [The Hacker News](https://thehackernews.com/2026/01/three-flaws-in-anthropic-mcp-git-server.html)
- `postmark-mcp` (npm): first malicious MCP server in the wild — version 1.0.16 (2025-09-17) added a BCC of all emails to the attacker; ~1,500 weekly downloads; sources conflict on whether the publisher account was compromised or the publisher was the attacker — search excerpt of [Koi Security](https://koi.ai/blog/postmark-mcp-npm-malicious-backdoor-email-theft)
- Archived reference servers still sit on npm with a "no longer supported" deprecation (`@modelcontextprotocol/server-github`, `-postgres`, `-puppeteer`, `-brave-search`) — [npm server-github](https://registry.npmjs.org/@modelcontextprotocol/server-github)

### Inferences
Enforce in OmniForge (ordered by value/effort):
1. **Never run an MCP server the user hasn't explicitly added**; show full command/URL; no auto-install from the registry; no `npx pkg@latest` — pin versions (registry gives `packages[].version`).
2. **Pin tool definitions** (hash of name/description/schemas/annotations) and re-prompt on change; surface a diff. This is the one control the spec says the protocol does *not* provide and that mcp-scan-style tools implement.
3. **Sandbox stdio servers by default** (srt on macOS or container), per-server env from Keychain, project-dir-only filesystem (read-only default), network off unless declared; log stderr and all calls to the audit trail.
4. **Human approval per mutating call**; annotations only *lower* friction when the server is user-trusted (annotations are untrusted by spec).
5. **Prompt-injection posture:** MCP results (and scraped pages OmniForge already handles) are untrusted data; do not allow a result from an open-world tool to silently trigger writes/commands/deploys; keep the roster small; apply progressive discovery to limit attack surface in context.
6. **Client-side SSRF/URL hygiene** for all OAuth/discovery/remote-server URLs using OmniForge's existing SSRF guard (HTTPS-only, private ranges blocked, redirects re-validated, DNS pinned); reject non-`http(s)` authorization URLs; never shell out to open URLs.
7. **OAuth:** CIMD + PKCE + `resource` + `iss` check (SDK) + own `state` check; per-issuer credential keys; tokens only in Keychain; no token passthrough (OmniForge must not forward a token issued for one server to another or to its own backend).
8. **Do not expose dangerous harness tools through OmniForge's own MCP server** and keep its HTTP form behind auth + Origin/Host validation (see §5).
9. Treat **CVE history as a version-floor list**: `mcp-remote` ≥0.1.16, Inspector ≥0.14.1, `mcp-server-git` ≥2026.1.14; add an advisory check (OmniForge already has an OSV check) for configured npm/PyPI servers.
10. Prefer the **scanner as a design reference**, not a dependency: Snyk Agent Scan is open source but sends server metadata to Snyk's API and needs a token, so a fully local pin/diff implementation is a better fit for OmniForge's privacy stance.

### Gaps
- Incident details (CVSS, fixed versions, download counts) come from news/security-vendor excerpts, not from NVD/GHSA pages fetched directly; discrepancies are flagged inline.
- Empirical injection success rates were not verified (secondary blog numbers were not used).
- No formal threat model of OmniForge's bridge was done; recommendations assume the sidecar bridge is already authenticated and loopback-only.

## 5. Should OmniForge also expose itself as an MCP server (analyze_url, get_investigation, compare, extract_features, rebuild_plan)?

### Takeaway
Yes, as a **second-phase, read-mostly** capability: the v2 server SDK makes a stdio server (desktop) and a stateless Streamable HTTP server (Vercel function, `createMcpHandler`) cheap to build, and it lets Claude Code/Cursor/Codex drive OmniForge's analysis without a new UI. Ship stdio-on-desktop first (no auth surface); add the remote form only with OAuth/token auth, Origin/Host validation and strict SSRF controls, and never expose the harness's file-write or run-command tools.

### Cited Findings
- `@modelcontextprotocol/server` 2.3.1 (Apache-2.0, Node >=20): `McpServer.registerTool(name, {description, inputSchema: z.object(...)}, handler)`; `serveStdio(factory)` from `/stdio`; `createMcpHandler(factory)` returns `{ fetch(Request) → Response }`; the factory runs once per HTTP request (stateless, "scales horizontally as-is"); serves both eras by default (`legacy: 'stateless'`) — [npm server](https://registry.npmjs.org/@modelcontextprotocol/server); [serving/http](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/serving/http.md); [protocol-versions](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/protocol-versions.md)

### Inferences
- **Benefit:** zero-UI access to OmniForge's unique analysis (fingerprinting, feature extraction, rebuild planning) from the agents developers already use; fits the bridge's existing "OmniForge ↔ coding-agent CLI" relationship in reverse (agent CLIs can call OmniForge). No duplication: no other server in the catalogue does this.
- **Proposed tool surface (all with `outputSchema` + `structuredContent`):**
  - `analyze_url(url, depth?)` — starts an analysis, returns `{investigationId, status}` immediately (poll with `get_investigation`; optionally also surface as an MCP Task later). Annotations: `readOnlyHint:false, destructiveHint:false, idempotentHint:false, openWorldHint:true`. Must reuse the SSRF guard; reject private targets; per-caller rate limits.
  - `get_investigation(id, sections?)`, `list_investigations()` — `readOnlyHint:true, openWorldHint:false`; large reports via resource links / `investigation://{id}/…` resource templates.
  - `compare(idA, idB)` — read-only.
  - `extract_features(id, filter?)` — read-only over stored evidence.
  - `rebuild_plan(id, constraints?)` — read-only planner output (a plan, never executes).
  - Do **not** expose: run command, write file, deploy, GitHub/Vercel mutation tools, API-key access.
- **Deployment order:** (1) desktop stdio server (`omniforge mcp` in the sidecar; users add it with `claude mcp add omniforge -- <path>`); (2) optional remote endpoint on Vercel via `createMcpHandler` with: bearer/OAuth auth (per-user investigations), `originValidationResponse`/`hostHeaderValidationResponse`, unguessable user-bound investigation IDs, scopes like `omniforge:read` / `omniforge:analyze`, request size/time caps. Web-origin exposure also raises abuse risk for `analyze_url` (open crawler) → require auth.
- **Prompt-injection toward the calling agent:** analysis outputs embed content scraped from untrusted sites; mark results as untrusted data, strip/escape active markup, and keep the `openWorldHint:true` annotation honest.
- **Effort/risk:** small code (tools are thin wrappers over `packages/core`), but the remote form creates a public attack surface — hence phase 2.
- Registering in the official registry makes OmniForge discoverable by any registry-aware client for free.

### Gaps
- No inspection of OmniForge's actual `packages/core` API surface, so tool names/inputs above are proposals mapped from the five names in the brief.
- Vercel function limits for long SSE responses/analyses unverified (vercel.com blocked).
- Per-CLI (Codex, Gemini CLI, OpenCode, Aider) MCP configuration syntax not verified.

## 6. Verified, ranked catalogue of free MCP servers for reverse engineering and app rebuilding (with duplication analysis and stale/archived flags)

### Inferences
**Overlap with OmniForge's existing features** (agent harness read/write/list/run tools; GitHub + Vercel REST integrations with branch+PR flow; crawler with SSRF guard; OSV vulnerability check; Monaco workspace; Repo Rip):
- High duplication → do not bundle: GitHub MCP (OmniForge has GitHub REST incl. branch+PR; remote OAuth needs a registered app), Vercel MCP (duplicates the Vercel REST integration and restricts clients to an approved list), reference `filesystem`/`git` (harness already does file I/O and commands), `fetch` and Firecrawl scrape/crawl (OmniForge crawler), Repomix (Repo Rip + harness read tools; could be used as a library instead).
- Low value: `memory`, `sequential-thinking`, `time`, `everything` (the harness already has task graphs; `everything` only for testing the client).
- Genuinely new: live DevTools (traces, heap snapshots, Lighthouse, network detail), interactive browsing (Playwright), current library docs (Context7), symbol-level code navigation (Serena), SAST (Semgrep — OmniForge only has OSV dependency checks), binary/APK decompilation (Ghidra, jadx, radare2), design-to-code (Figma-Context), shadcn registry lookup, web search (Exa/Tavily).

**Ranked recommendation** (criteria: new capability for RE/rebuild, free, maintained, transport/sandbox fit, licence risk):
| Rank | Server | Why | Caveats |
|---|---|---|---|
| 1 | Chrome DevTools MCP | Network/console/perf/heap inspection of target apps; very active; Apache-2.0; stdio | Desktop-only; Chrome required; disable telemetry (`--no-usage-statistics --no-performance-crux`); it can read/modify anything in the controlled browser — use isolated profile |
