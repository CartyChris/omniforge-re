## 1. What is the most reliable, low-maintenance way to obtain correct, up-to-date starter projects per stack (official scaffolders via the bridge vs giget vs shipping our own), and which need network at generation time?

### Takeaway
Official scaffolders are the freshest source (all but create-t3-app were released within the last ~7 weeks) and most expose non-interactive flags, but they differ in whether the templates are bundled in the npm package (offline after download: create-vite, create-next-app, create-t3-app, create-vue, sv, create-qwik, create-analog) or fetched from GitHub/npm at run time (create-astro, nuxi, create-react-router, create-solid, create-expo). The most robust low-maintenance design is a hybrid: run the official CLI non-interactively on the desktop (bridge, pinned version, Node-engine check), and on the web/serverless path extract templates as data from the immutable npm tarball (bundled-template packages) or via giget from a pinned GitHub ref - never execute CLIs in a serverless function - and ship own minimal templates only for stacks with no JS scaffolder.

### Inferences
- Local tarball inspection (Python scripts run against `registry.npmjs.org` tarballs) shows which scaffolders carry their templates: bundled = create-vite, create-next-app, create-t3-app, create-vue, create-qwik, create-analog, sv, create-electron-vite; run-time GitHub/npm fetch = create-astro, nuxi, create-react-router, create-solid, create-expo. This is a code-grep result, not vendor documentation, so re-verify per version.
- Because an npm tarball is immutable and addressable by `name@version` from `registry.npmjs.org` (reachable from serverless), "download tarball and copy the `template-*` directory" gives a pinned, cacheable, no-code-execution template source for the bundled-template group; giget with a pinned `#ref` does the same for GitHub-hosted templates. This avoids running `npx` inside Vercel functions.
- On the desktop, running the official CLI through the bridge keeps templates current with zero maintenance, but the bridge must (a) check `node -v` against the engine floors above (several now require >=22.22), (b) pass non-interactive flags (`--yes`, `--skip-install`/`--no-install`, `--no-git`), (c) treat scaffolders that execute lifecycle scripts or community add-ons (yo generators, `sv --add` community add-ons, `postinstall`) as untrusted code needing approval.
- Shipping our own templates is only justified for (1) the static-HTML and Vite+React fast path that must work offline in the browser, and (2) stacks without a JS scaffolder where a permissively-licensed community template or a minimal hand-written skeleton is sufficient (Go, Rust/Axum, Swift). Each shipped/fetched template should record its source licence (SPDX) in the generated project's provenance.
- Registry content (21st.dev, Aceternity) must be licence-checked per item; Magic UI and shadcn core are MIT and safe defaults.

- No GitHub last-commit or archived status could be read (api.github.com/repos/* blocked), so "stale" rests on npm/Go-proxy/PyPI release dates only.
- Exact template licences inside each scaffolder's output (e.g. whether every Astro `examples/*` folder is MIT) were not audited.
- Flag sets for nuxi, create-tauri-app and create-expo were seen in READMEs only partially (e.g. nuxi `init` flags not documented in its README); verify with `--help` at implementation time.
- Laravel (`laravel new`), Flutter/Swift/Rails scaffold commands and their offline behaviour were not verified beyond licences.
- 21st.dev's own terms of service and install caps could not be fetched; Aceternity text is from a search summary.

## 2. Can full-stack/Node previews run in the browser for free under permissive terms? (WebContainers licensing for non-StackBlitz production sites, and alternatives)

### Takeaway
WebContainers: the `@webcontainer/api` client is MIT on npm, but it depends on StackBlitz-hosted proxies/acceleration and StackBlitz's Terms of Service, and StackBlitz's official "Commercial Usage" page says production use in a for-profit setting requires a paid WebContainer API licence (prototyping/POC free). That page could not be fetched verbatim here, so the exact wording and any free-usage cap must be re-checked by a human. For a commercial OmniForge, treat WebContainers as not free. Free permissive in-browser options are thin: Sandpack's static/React bundler (Apache-2.0, already used) and the young MIT `almostnode`; Nodebox (the Sandpack "node" template runtime), CheerpX and BrowserPod are licence-restricted for businesses.

### Inferences
- OmniForge is a studio that rebuilds apps for users; if it is operated for profit, a WebContainers preview inside it is "production use in a for-profit setting" and needs a StackBlitz licence. Even if it is non-commercial today, the hosted-proxy dependency and ToS acceptance make it a vendor dependency rather than a free open component.
- The Vercel SPA can set COOP/COEP via `vercel.json` headers, but doing so site-wide breaks embedding of third-party iframes and Sandpack's cross-origin bundler iframe unless they send CORP/credentialless headers; a dedicated `/preview` route/subdomain with isolation is the safer pattern (not tested here).
- Do not enable Sandpack's Nodebox-backed "node" templates in a commercial build: the Nodebox licence forbids it, and `sandpack-client` pulls Nodebox as a dependency (licence audit of the lockfile should flag `@codesandbox/nodebox` with the custom "Sustainable Use" licence). The React/static templates use the Apache-2.0 bundler.
- Practical free path: keep Sandpack (static/React) for client-only previews, use the desktop bridge dev server for real full-stack previews, and prototype `almostnode` behind a feature flag for Vite/Next-style previews, accepting its experimental status and its emulation of Node 20 APIs only (native modules stubbed). Back-end mocking in the browser can use msw + PGlite/sql.js.

### Gaps
- Verbatim text and current limits of `webcontainers.io/enterprise` and StackBlitz ToS were not retrievable (host blocked). A human should read https://webcontainers.io/enterprise before any decision.
- No test of almostnode against real generated projects (Next.js, SvelteKit, Nuxt) was run; its compatibility claims are README-only.
- Whether the Vercel SPA can keep COOP/COEP isolation alongside the existing Monaco/Sandpack iframes, and whether Tauri's macOS webview supports SharedArrayBuffer with those headers, was not researched.
- BrowserPod free-tier limits and attribution requirements are unknown; CodeSandbox free SDK limits conflict between sources.

## 3. What is the best Node-only pipeline to compare reference vs rebuilt screenshots/DOM (no native deps) and produce a scored, evidence-linked discrepancy list an agent can repair?

### Takeaway
Playwright (`playwright-core`, Apache-2.0, 0 dependencies, drives an existing Chrome) for capture + ARIA/DOM/style facts, `pixelmatch` 8 (ISC, pure JS) or `@blazediff/core-wasm` (MIT, WASM) for pixel diffs, `looks-same` 10 (MIT, WASM PNG) for diff clusters, and `axe-core` (MPL-2.0) for accessibility deltas form a pipeline with no native Node addons. Scoring and repair-loop logic still has to be written; BlazeDiff's agent package is the closest prior art but pulls in sharp and LangGraph.

### Inferences
- A rebuilt app will not share DOM structure with the reference, so DOM comparison should match elements by role + accessible name + visible text (from the ARIA tree / `getByRole`), then compare box, computed style and contrast; matching by DOM path (as in the PoC) is only a stand-in. Pixel diffs of non-identical rebuilds are noisy, so pair `windowSize`-style local density, SSIM (`@blazediff/ssim` or `ssim.js`) and cluster boxes (looks-same) and map each cluster back to the nearest element box to produce an evidence-linked finding {viewport, cluster bbox, element selector/role/name, diff %, screenshot paths, axe rule, ARIA delta, severity score}.
- Severity score proposal: weight by cluster area x viewport importance x element role (headings/buttons/inputs higher), add axe impact (critical/serious) and ARIA-tree delta; mark low-density scattered diffs as "noise" the way BlazeDiff's heuristic verdicts do. This scoring layer does not exist in any library found and must be built.
- Determinism needs: fixed viewport and `deviceScaleFactor`, `animations: 'disabled'`, HAR replay or request mocking for the reference, font loading wait, and masking of dynamic regions; Playwright warns that screenshots differ across platforms/browsers, so reference and rebuild must be captured on the same machine/browser build.
- Desktop (Tauri sidecar): `playwright-core` + a locally installed Chrome (`channel: 'chrome'` / `CHROME_PATH`) works inside a Bun-compiled binary per the local test; add the two `--external` flags to the build. Serverless: running Chromium in a Vercel function is possible in principle via `@sparticuz/chromium(-min)`, but function size/duration limits were not verified (Vercel docs search returned no limit numbers) - prefer doing capture on the desktop or in an external runner and keeping the web app to the comparison math (pixelmatch/BlazeDiff-WASM/looks-same are browser- and Worker-safe).
- Avoid for the "no native deps" requirement: sharp (and therefore `@argos-ci/core`, `@blazediff/agent`), odiff-bin, `@blazediff/*-native`, resemblejs/canvas. LGPL pa11y and diff-dom add licence obligations; axe's MPL-2.0 is acceptable if not modified.

### Gaps
- The PoC compared two hand-made pages; accuracy on real, differently-structured rebuilds (and false-positive rates of the proposed scoring) is untested.
- Playwright codegen and trace-viewer documentation were not read directly; the codegen claim rests on the BlazeDiff agent README.
- Playwright `toHaveScreenshot` comparator options beyond pixelmatch (e.g. a newer SSIM-based comparator) could not be confirmed: the options page fetched did not mention one.
- Vercel function bundle-size/duration limits for headless Chromium were not obtained (documentation search returned unrelated snippets).
- Whether `@blazediff/core-wasm` exactly matches pixelmatch on real screenshots was only tested on a synthetic rectangle.
- Windows/Linux behaviour of the Bun-compiled Playwright pipeline was not tested (only Linux x64 here; the shipped target is macOS Tauri).

## 4. Which deploy providers offer a simple, documented REST API for file-upload deploys that works from a browser/serverless function with a user token on free plans?

### Inferences
- Replace ad-hoc licence detection with a layered classifier: (1) read `package.json`/`pyproject`/`Cargo.toml` SPDX expressions and validate with spdx-expression-parse (never trust spdx-correct output without showing it as a "guess", and never accept its MIT/Apache collapse); (2) for LICENSE text use license-similarity but treat "no match" and known-confusable results (MPL variants, GPL "only" vs "or-later") as "needs review"; (3) maintain an explicit table of non-SPDX/source-available licences (Sustainable Use, MSCL, FSL-1.1-Apache-2.0 alias, CheerpX, BrowserPod ToS, Wasmer "Modified MIT") and a copyleft/strong-copyleft/weak-copyleft class derived from SPDX `isOsiApproved` + a hand-maintained map; (4) on the desktop optionally call ScanCode or ClearlyDefined for deep scans. A Node >=22 compatible library with no native addons: spdx-expression-parse, license-similarity (verified in Node and a Bun-compiled binary).
- license-similarity's footprint (~8 MB data, 1-4 s on long texts) suggests running it in the serverless function or sidecar, not the browser bundle; its 0.2.x version and single maintainer are a maintenance risk, so pin and wrap it behind an interface.
- secretlint fits the existing preflight secret check as a drop-in rule engine (pure JS, Node >=22); gitleaks rule data (MIT) can enrich it; keep TruffleHog out of the product because of AGPL-3.0.
- SBOM: generate CycloneDX for each rebuilt project with the pure-JS library from lockfile data (or call `cyclonedx-npm`/`cdxgen`/`syft` via the bridge); vulnerability matching stays on OSV.dev (already integrated) with osv-scanner as an optional offline CLI.
- Local test showed the library set compiles into a Bun single-file binary with `--external` flags for the optional CycloneDX plugins, so the sidecar can include them; native-binary tools (odiff, `*-native`, sharp, wrangler's workerd) cannot be bundled that way.

- Secretlint rule quality (false positives/negatives) versus gitleaks was not measured; `@sanity-labs/secret-scan` (1,100+ rules from TruffleHog detectors) licence/derivation was not checked, and deriving rules from AGPL TruffleHog detectors may carry licence implications.
- JS-based vulnerability scanning beyond OSV (retire.js database coverage) was not evaluated.
