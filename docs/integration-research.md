# Fix the licence gate, then integrate five tools

OmniForge RE should repair its own licence gate first and then integrate, in order, a Playwright-based compare engine, a sandboxed JavaScript deobfuscator, a WASM multi-language parser, a CLI-direct coding-agent runner and a curated skills pack; seventeen further candidates follow, and about a hundred named alternatives are rejected. The gate comes first because I ran the existing [`repo/license.ts`](../packages/core/src/repo/license.ts) on real licence texts: it labels the Convex backend's source-available FSL-1.1 as Apache-2.0 "permissive" with no attestation required, reads MPL-2.0 and Directus's MSCL as GPL-3.0, and returns UNKNOWN for pixelmatch's ISC text, while the lockfile already carries `@codesandbox/nodebox@0.1.8`, whose Sustainable Use License limits use to internal-business or non-commercial purposes and which Sandpack's `vite-react-ts` template (the one the app selects for Vite projects) is configured to run on. The first four build-now items are pure JS/WASM or already-owned dependencies that the note authors executed on Linux x64 (Node 22.22.0, Bun 1.4.2), including inside `bun build --compile` binaries; the CLI-direct runner is the largest capability gain, but no note ran any agent CLI, so its parsers must be built from transcripts captured on real installs. Nothing was run on macOS (OmniForge ships an Intel build) or on Vercel, so every platform-fit statement for those two targets is inference. By my estimate the whole backlog is about 87 engineer-days, 19 of them for the first five items, and nine decisions belong to the owner, led by Nodebox and WebContainers, a Wappalyzer-format importer, bundling Java-based tools, and whether browser MCP servers, which operate outside OmniForge's robots and SSRF guard, may ship at all.

## Two defects in OmniForge's own licence plumbing outrank every new tool

Every recommendation here leans on the owner's rule that copyleft and source-available code stays out of the bundle, and the code that enforces it for Repo Rip is weaker than the research assumed. [`detectLicenseText`](../packages/core/src/repo/license.ts) walks a list of regex signatures and returns the first hit, so a text that merely quotes another licence is misfiled. I fetched the current licence texts used in the notes and ran the function directly on Linux; the real flow may add repository-host metadata, which I did not exercise.

| Licence text | Detector returned | Correct | Consequence |
|---|---|---|---|
| [Convex backend LICENSE.md](https://raw.githubusercontent.com/get-convex/convex-backend/main/LICENSE.md) (FSL-1.1-Apache-2.0) | Apache-2.0, permissive | Source-available, bars "Competing Use" | `assessRip` returns level "attribution" and `requiresAttestation: false` |
| [Directus license](https://raw.githubusercontent.com/directus/directus/main/license) (MSCL) | GPL-3.0, strong copyleft | Source-available | Wrong class |
| [axe-core LICENSE](https://raw.githubusercontent.com/dequelabs/axe-core/HEAD/LICENSE) (MPL-2.0) | GPL-3.0, strong copyleft | MPL-2.0, weak copyleft | Over-restrictive; would flag a dependency we want |
| [pixelmatch LICENSE](https://raw.githubusercontent.com/mapbox/pixelmatch/HEAD/LICENSE) (ISC) | none, so UNKNOWN and attestation required | ISC, permissive | Over-restrictive; line-wrapped text defeats the regex |
| Nodebox LICENSE ([installed copy](../node_modules/.pnpm/@codesandbox+nodebox@0.1.8/node_modules/@codesandbox/nodebox/LICENSE)) | none, so UNKNOWN | Sustainable Use License | Safe by accident |
| [pa11y](https://raw.githubusercontent.com/pa11y/pa11y/HEAD/LICENSE), [TruffleHog](https://raw.githubusercontent.com/trufflesecurity/trufflehog/main/LICENSE), [webcrack](https://raw.githubusercontent.com/j4k0xb/webcrack/HEAD/LICENSE), [Monolith](https://raw.githubusercontent.com/Y2Z/monolith/HEAD/LICENSE) | LGPL-3.0, AGPL-3.0, MIT, CC0-1.0 | same | Correct |

The unsafe direction is the first row: the one genuinely source-available text in the set passed as permissive, which is exactly the class the owner's rule exists to catch. The generation note proposed replacing ad-hoc detection with `license-similarity`, but its own tests show that library missing LGPL-3.0 (which the existing detector gets right), mislabelling MPL-2.0 as `MPL-2.0-no-copyleft-exception`, returning nothing for FSL, MSCL and the CheerpX licence, and taking one to four seconds on long texts ([generation note §6](research/generation_verification_deploy_compliance.md)). Neither tool is adequate alone, so the plan keeps the deterministic detector, normalises whitespace, puts specific signatures (FSL, MSCL, MPL, Sustainable Use, Business Source, CheerpX) ahead of the GPL family, adds a maintained table of non-SPDX and source-available licences, and validates manifest `license` fields with `spdx-expression-parse`, which parses `(MIT OR Apache-2.0)` correctly and rejects non-SPDX spellings instead of silently collapsing `MIT/Apache-2.0` to `Apache-2.0` as `spdx-correct` does.

The second defect is already shipped. The lockfile pins [`@codesandbox/nodebox@0.1.8`](../pnpm-lock.yaml), a dependency of `sandpack-client` per the generation note; its installed LICENSE is the Sustainable Use License, Version 1.0, which allows use "only for your own internal business purposes or for non-commercial or personal use" and distribution only "free of charge for non-commercial purposes", and the production bundle contains the Nodebox client with its `https://nodebox-runtime.codesandbox.io` endpoint. In the installed `@codesandbox/sandpack-react` 2.20.0 the `vite-react` and `vite-react-ts` templates declare `environment: "node"`, while `react-ts` declares `create-react-app`; [`SandpackPreview.tsx`](../apps/web/src/components/workspace/SandpackPreview.tsx) picks `vite-react-ts` whenever `src/main.tsx` exists, which is the normal layout of a Vite rebuild. I did not run the preview in a browser, so I have not confirmed that Nodebox loads for that template at run time, only that the template and the bundle are wired to it. The generation note's advice that "the React/static templates use the Apache-2.0 bundler" is therefore not true of the template this app chooses; whether the situation is acceptable depends on the owner's commercial intent (decision 1 below).

One piece of step 2 is already underway: the working tree holds an uncommitted `packages/core/src/verify/` module (131 lines across `structure.ts` and `report.ts`), `packages/core/test/verify.test.ts`, pixelmatch and pngjs added to `packages/server/package.json`, and a 24-line change to `bridge/render.ts`. I listed and skimmed these but did not review or run them, so the 3-day estimate for the compare engine is "finish and harden", not "start".

## Only pure JS and WASM run in all four places, and only some of it was proven

Four execution targets constrain every pick. The browser SPA takes pure JS and WASM; no candidate in any note was executed in a browser. A Vercel function runs Node, but no note retrieved function size, memory or duration limits (the docs search returned only `vercel.json` examples such as `"memory": 3009, "maxDuration": 60`), and the app itself has not been deployed to the owner's team ([FEATURES.md](../FEATURES.md)), so every Vercel fit is reasoning. The Bun-compiled sidecar runs JavaScriptCore rather than V8, which is why webcrack's default `isolated-vm` sandbox fails there ("No native build was found ... runtime=node") and why the QuickJS substitution matters; Bun can embed WASM only through `with { type: "file" }` or a single-file build, because the default QuickJS variant looked for `/$bunfs/root/emscripten-module.wasm` and failed ([web note §1](research/web_capture_and_deobfuscation.md)). Spawned CLIs run on the user's machine and inherit its Java, .NET and Node versions; Node floors reached 22.22 for create-astro and create-react-router and 22.22.3 for create-analog and the Angular CLI, and Java floors run from 11 (jadx) through 17, 21 and 25 (Ghidra) ([generation note §1](research/generation_verification_deploy_compliance.md), [code note Q4](research/code_binary_app_analysis.md)).

Compiled-binary results are the strongest evidence in the set. The Bun hello-world baseline is 81.3 MB; webcrack with the QuickJS single-file sandbox adds 4.2 MB, and adding prettier, pixelmatch, looks-same and pngjs brings the total to +8.5 MB; web-tree-sitter with grammars adds 2.2 MB; the compare pipeline compiled and ran from a directory without `node_modules` once `--external 'chromium-bidi/*' --external electron` was passed. Compiled failures are equally informative: Lighthouse crashed at start-up looking for `/$bunfs/root/locales/`, `@ast-grep/wasm` fails under Bun in both `run` and `--compile` forms (while `@ast-grep/napi` works, at +16.4 MB), and `tree-sitter-wasms@0.1.13` cannot load under web-tree-sitter 0.26 or 0.27 because its WASM files carry a legacy `dylink` section. Intel macOS is the quiet gap: `isolated-vm` 6.2.0 has no `darwin-x64` prebuild, wakaru's npm packages list no `darwin-x64` binary, Noir and Monolith Intel builds are unconfirmed, and OmniForge's own Intel app was cross-built but never launched ([FEATURES.md](../FEATURES.md)). The hosted app's only route to JVM and Go tools is a Vercel Sandbox microVM, whose pricing and limits no note retrieved; AGPL tools must never run there for other users.

The evidence splits cleanly. Executed by note authors on Linux x64 with Node 22.22.0 and Bun 1.4.2: webcrack, the QuickJS sandbox and its containment, wakaru's Linux binary, prettier, pixelmatch, looks-same, odiff, Crawlee (which crawled a robots-disallowed path and `127.0.0.1` by default), the full Playwright compare pipeline in Node and in a compiled binary (with Chromium 141 in that sandbox), the SPDX and CycloneDX libraries in a compiled binary, `license-similarity` on about twenty texts, web-tree-sitter on six languages, ast-grep napi and wasm, vector-search micro-benchmarks, one Lighthouse run on Node, and live paging of the official MCP registry. Checked by me: the licence-detector results, the Nodebox files and template wiring, the `pixelmatch` dependency list, and the repo's current state. Everything else, including every agent CLI, every MCP server, Noir, jadx, Apktool, Ghidra, the deploy APIs, secretlint, retire's scan API, the embedding models and every macOS or Vercel claim, was read from registry metadata, documentation or source. The macOS CI workflow described in FEATURES §12 already builds both architectures on GitHub runners; adding a job that runs the compiled-sidecar tests for rows 2 to 4 there would convert the biggest block of "read" on macOS into "tested" at almost no research cost.

## Delegate editing to user-installed agents, and pin every skill and MCP tool

The workflow that matters most is the CLI-direct contract, and its shape is consistent across the notes ([agents note](research/agents_skills_memory_rag.md)): copy or `git worktree add` the approved folder into a scratch directory with a baseline commit, run the CLI inside `srt` with write access limited to that directory and a network allowlist of the model host, pass explicit bounds, parse the event stream for progress, compute `git add -A && git diff --binary` when it exits, show the diff in the existing panel, and apply to the real folder only after approval. Every CLI named has a headless mode with machine-readable output except aider, whose diff comes from git: Claude Code `-p --output-format stream-json --verbose` ([docs](https://code.claude.com/docs/en/headless)), Codex `exec --json` with typed `file_change` items ([source](https://github.com/openai/codex/blob/HEAD/codex-rs/exec/src/exec_events.rs)), Gemini CLI `-p --output-format stream-json` ([docs](https://github.com/google-gemini/gemini-cli/blob/HEAD/docs/cli/headless.md)), and opencode `run --format json` ([docs](https://github.com/anomalyco/opencode/blob/HEAD/packages/web/src/content/docs/cli.mdx)). A security trap sits in the first of these: without `--bare`, `claude -p` runs the folder's `.claude/settings.json` hooks and connects its `.mcp.json` servers with no trust dialog, which is dangerous in a ripped repository, yet `--bare` never reads OAuth or the keychain and needs `ANTHROPIC_API_KEY`. Either the user supplies an API key or the scratch worktree must be stripped of `.claude/`, `.mcp.json` and `CLAUDE.md` before launch; the stripping route is my design suggestion and is untested. Anthropic's documentation also forbids third parties from offering claude.ai login through the Agent SDK, so the runner must spawn the user's own logged-in CLI or use their API key, and must not bundle the proprietary `@anthropic-ai/claude-agent-sdk` ([docs](https://code.claude.com/docs/en/agent-sdk/overview)). Gemini CLI should be offered to API-key users only, because its README says unpaid and Google One users moved to a different CLI on 2026-06-18. A second workflow, absent from every library surveyed, is the compare, score and repair loop: map each pixel cluster back to the nearest element by role and accessible name, weight by cluster area, viewport and role plus axe impact, and hand the ranked list to the agent; BlazeDiff's agent package is the nearest prior art but pulls in sharp and LangGraph ([generation note §3](research/generation_verification_deploy_compliance.md)). The existing harness needs only two further tools to run aider's test-repair loop natively, `run_tests` with structured failures and `apply_patch`, so no agent framework is warranted.

The skills pack is cheap and licence-clean if handled per file. Anthropic's four chosen skills each carry an Apache-2.0 `LICENSE.txt`, while its docx, pdf, pptx and xlsx skills are proprietary and `doc-coauthoring` has an empty licence file; the identical-looking `frontend-design` under `anthropics/claude-code/plugins` sits in a proprietary-licensed repository, so only the `anthropics/skills` copy is usable ([agents note](research/agents_skills_memory_rag.md), [repo](https://github.com/anthropics/skills)). The two Vercel skills carry `license: MIT` only in frontmatter with no repository LICENSE, so they are conditional on the owner's comfort; superpowers is MIT but its brainstorming visual companion loads a logo from the vendor's site by default, so exclude that skill. The loader should follow the spec's three-tier disclosure and treat project-scope skills from an untrusted repo as inert until the user trusts them. Because Claude Code ignores `AGENTS.md` when any `CLAUDE.md` exists, generated projects should emit both. No note found a benchmark showing these skills improve output, so the right claim is "shipped and measured with the compare engine on five fixture sites", not "improves quality".

MCP is where the notes' enthusiasm outruns what OmniForge needs. Spawned CLIs can load MCP servers themselves, and Claude Code accepts `--strict-mcp-config --mcp-config` ([docs](https://code.claude.com/docs/en/cli-reference)), so a cheap interim path is to pass the user's approved server list through to the CLI (about two days, other CLIs' flags unverified); the native client is justified for OmniForge's own harness and local-model users, and for the pin, approve and audit experience. Build it on the v2 SDK, whose root entry is runtime-neutral while `StdioClientTransport` lives under `/stdio` and so belongs only in the sidecar ([packages doc](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/get-started/packages.md)). The security controls the MCP project itself prescribes are all in scope: hash each tool's name, description, schemas and annotations at first approval and re-prompt on any change, because the protocol offers no defence against rug pulls; treat annotations as untrusted; show the exact untruncated command and pass only declared secrets; sandbox stdio servers; reuse the SSRF guard for OAuth discovery; compare the OAuth `state` ourselves because the SDK does not ([local-server security](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/docs/2026-07-28/tutorials/security/local-server-security.mdx), [OAuth doc](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/main/docs/clients/oauth.md)). Do not implement Roots, Sampling or Logging, which the 2026-07-28 revision deprecates. Discovery inside the app should use only the [official registry](https://raw.githubusercontent.com/modelcontextprotocol/registry/main/docs/reference/api/official-registry-api.md): unauthenticated, `access-control-allow-origin: *`, CC0 metadata, at least 4,000 entries in a live check, but with lookalike and lagging entries, so it is a search box, never an installer. ## Rebuilding from binaries, bundles and sites needs adapters, not frameworks

On the input side, the caveats that the table cannot carry are these. For JavaScript recovery, webcrack was tested on one synthetic obfuscator.io sample and one small webpack bundle only; Browserify, Parcel, Vite, Rollup, esbuild and other obfuscators were not tested, and it reported no bundle for the newest webpack 5.112 output, so the report must say "not unpacked" instead of skipping silently, with wakaru as the optional second opinion (it also lists esbuild, Bun and Metro support) ([web note §1](research/web_capture_and_deobfuscation.md)). The sandbox's worst case is 10 to 14 seconds per call, a budget nobody has checked against Vercel limits. Deobfuscation should run only on resources the crawler fetched under robots and rate limits, and never be aimed at CAPTCHA or anti-bot challenge scripts; that guardrail is my addition, consistent with the owner's rule. The existing `sourcemap.ts` already recovers `sourcesContent`, so sourcemapper and unwebpack-sourcemap add nothing.

For source analysis, tree-sitter plus Noir covers structure and endpoints without a copyleft tool, and ast-grep is deferred for three reasons: its WASM build breaks under Bun, its other-language packs use postinstall scripts, and its WASM package peers on `web-tree-sitter ^0.26` while the tested stack pins 0.27.1. Repomix's MIT queries for sixteen grammars would save query-writing, but they target a different grammar bundle (tested only under web-tree-sitter 0.26.8), so their compatibility with the VS Code grammars is unverified. No permissively licensed rule pack for route inventory exists: Semgrep's official rules sit under a licence that forbids competing products, and its text was not readable from the sandbox. For fingerprints, retire.js adds versioned library detection (76 libraries in a 604 KB data file) that OmniForge's 162 rules lack; the large Wappalyzer-lineage dataset (7,646 apps) is GPL-3.0 and Nuclei's MIT templates are mostly active probes that would breach the rate-limit posture, so breadth beyond retire.js depends on decision 3. For apps, an IPA is a zip with plists that parse in-process, but App Store binaries are FairPlay-encrypted, so the report must say "needs a decrypted dump" when `cryptid` is 1, never imply readable source; Electron `.asar` extraction is a 126 KB library; `ilspycmd` needs a .NET 10 SDK and mostly duplicates REA, so it is unscheduled.

For outputs, the scaffold catalogue should run official CLIs only through the approval gate (they execute third-party code), check `node -v` against each `engines` floor, record the template source and SPDX in provenance, and use immutable npm tarballs or giget with a pinned ref on the hosted path instead of `npx` in a function. Template licence audits inside each scaffolder were not done. For deploys, Cloudflare's documented path is Workers Static Assets, because Pages direct upload via REST relies on an undocumented asset protocol; Netlify caps API deploys at 3 per minute and 100 per day per a search summary; GitHub Pages' policy excludes commercial or SaaS sites and constrains clones, so it should not be offered for rebuilt third-party sites. For previews, keep Sandpack but resolve the Nodebox question; treat `almostnode` (MIT, experimental, Node 20 emulation, 15.6 MB) as a feature-flagged spike; use PGlite, sql.js and msw for browser-side data mocks. The inputs the notes did not research at all are PDF text extraction, design-token and Figma import (only `style-dictionary` and Figma's REST types were glimpsed), Unity IL2CPP and Flutter AOT decompilation, container sandboxes through Docker or Podman, Tauri's WKWebView behaviour under the COOP and COEP headers WebContainers would need, and Expo Snack or SwiftUI previews.

## What this report cannot tell you

GitHub's API was blocked, so recency rests on registry publish dates, Go-proxy dates, atom feeds and, where noted, last-commit dates read from clones, and star counts are rounded page values. Vendor documentation hosts for WebContainers, Netlify, Cloudflare, Semgrep, Render, Fly and others were unreachable, so quotas and prices come from search summaries and must be re-verified before they appear in UI text. No agent CLI, MCP server, Noir, jadx, Ghidra or deploy API was executed, and no embedding model could be downloaded, so quality claims about generation, skills and retrieval are unmeasured. The effort figures are mine, from reading scope rather than from comparable past work, and could be off by a factor of two in either direction for rows 5 and 12 in particular. Legal readings (AGPL network use, Semgrep Rules License, FSL, MSCL, Sustainable Use) are inferences, not advice.

## Conclusion

The research was framed as a hunt for more tools, but the sharper finding is that OmniForge's constraint is its instruments, not its inventory: a licence gate that passes a source-available repository as permissive and a preview path wired to a non-commercial runtime mean the "never bundle copyleft or source-available" rule is not yet enforceable, and without a visual compare engine no claim that a skill, a CLI run or a scaffold improved a rebuild can fail. Building those two instruments first is what turns the remaining twenty candidates from opinions into tests, which is why the plan spends its first five items on gate, measurement, two cheap read-side wins and one large delegation step.

Two further consequences follow. The MCP ecosystem looks larger than it is: once spawned CLIs can load their own servers, OmniForge needs a native client mainly for its own harness and for pin-and-approve safety, and only five servers (Chrome DevTools, Playwright, radare2, Ghidra, Context7) earn a preset, none of them without the owner settling how browser tools relate to the crawl policy. And the evidence is Linux-shaped: the one inexpensive way to shrink the "read only" column is to run the compiled-sidecar tests for rows 2 to 4 on the macOS runners the repo already uses, on both architectures, before any of the Intel-specific doubts in this report harden into shipped promises.
